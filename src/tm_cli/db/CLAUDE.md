# db domain

Last verified: 2026-05-06 (CLI in `tm_cli.cli` is now the primary consumer)

## Purpose
Persistence layer for content imported from external sources (Confluence, etc.), the glossary of important terms extracted from that content, the agent's work-in-progress observations about the threat model, and the structured Data Flow Diagram (DFD) it builds up. Pydantic is the schema source of truth; sqlite3 is the storage engine.

## Contracts
- **Exposes** (re-exported from `tm_cli.db`): `connect`, `init_schema`, `Document`, `DocumentCreate`, `DocumentUpdate`, `DocumentSummary`, `DocumentRepository`, `Term`, `TermCreate`, `TermUpdate`, `TermRepository`, `Observation`, `ObservationCreate`, `ObservationUpdate`, `ObservationType`, `ObservationStatus`, `ObservationRepository`, `Tactic`, `ThreatCatalogCreate`, `ThreatCatalogEntry`, `ThreatCatalogRepository`, `ThreatCreate`, `ThreatUpdate`, `Threat`, `ThreatRating`, `ThreatRepository`, `FindingSeverity`, `ValidationFinding`, `ValidationFindingCreate`, `ValidationFindingUpdate`, `ValidationFindingRepository`.
- **Guarantees**:
  - `last_imported` is **always** set by the repository on every `create` and `update` for documents (callers never pass it).
  - `last_updated` on **documents** is caller-supplied (source author's update time).
  - `last_updated` on **terms** and **observations** is repository-managed — set on every `create` and `update`. Both are produced internally; there is no caller-supplied source-of-truth timestamp.
  - `terms.term` is UNIQUE; `TermRepository.create` raises `sqlite3.IntegrityError` on duplicates.
  - `document_terms` is a junction table (composite PK on `document_id, term_id`) with `ON DELETE CASCADE` on both FKs. Deleting either side prunes the link rows; the other side is untouched.
  - `TermRepository.link` is idempotent (uses `INSERT OR IGNORE`).
  - `observations.observation_type` is constrained at two layers: a Pydantic `Literal["potential_threat", "incomplete_information", "question", "todo"]` (`ObservationType`) and a SQL `CHECK` constraint. Invalid values fail at the model layer; raw SQL writes still hit the CHECK.
  - `observations.status` is similarly constrained — `ObservationStatus = Literal["open", "closed"]` plus a SQL `CHECK`. New observations default to `"open"` (Pydantic default and SQL `DEFAULT 'open'`).
  - `list()` on documents returns `DocumentSummary` (no `content` field). `content` is potentially large; only `get(id)` reads it.
  - `list()` on terms and observations returns full rows — neither has a large blob to elide.
  - **Every repo exposes `search(text=None, *, <filters>, limit=None, offset=0)`** returning the same model `list()` returns. `text` is whitespace-tokenized; tokens are AND'd, each token must match (case-insensitively, with `%`/`_` escaped) at least one of the repo's searchable text columns. Empty/whitespace-only `text` is equivalent to `list()` with the same filters. DFD repos take `diagram_id` as the first positional arg (mirrors `list()`). `DocumentRepository.search()` projects `DocumentSummary` (LIKE happens against `content`, but the column is not returned).
  - `connect()` commits on clean exit, rolls back on exception, always closes.
  - Datetimes returned from reads are `datetime` objects (not strings) thanks to registered converters.
- **Expects**: `TM_DB_PATH` env var set when `connect(path=None)` is called. Tests can pass `path` explicitly.

## Dependencies
- **Uses**: stdlib `sqlite3`, `pydantic`, `pathlib`.
- **Used by**: `tm_cli.cli.*` (every entity command module imports the relevant repo + Pydantic models from `tm_cli.db`), `tm_cli.cli._introspection` (for JSON Schema), `tests/fixtures/seed.py`.
- **Boundary**: do NOT import from `tm_cli.main` or any CLI surface here — this layer is callable from any context.

## Key Decisions
- **stdlib sqlite3 over SQLModel/SQLAlchemy**: minimal deps, full SQL control, schema is one short DDL string.
- **STRICT tables**: enforces declared column types at the DB layer.
- **`INTEGER PRIMARY KEY` (not `AUTOINCREMENT`)**: ROWID-based; faster, no `sqlite_sequence` side table. We don't need the never-reuse-id guarantee.
- **Datetimes stored as ISO 8601 TEXT**, not unix epoch INTEGER. Human-readable when poking with the `sqlite3` CLI; tradeoff is ~19 bytes/row vs INTEGER. Switch to INTEGER if/when timestamp range queries become hot.
- **`register_adapter(datetime, ...)` / `register_converter("datetime", ...)`** registered at module-import time in `connection.py`. SELECTs use `AS "col [datetime]"` aliases (PARSE_COLNAMES) to drive conversion — STRICT forbids `datetime` as a declared column type.
- **`DocumentSummary` separate from `Document`**: callers pick the cost. `list()` never reads content; `get()` does.
- **LIKE-based search, not FTS5**: `search()` on every repo uses case-insensitive `LIKE` with explicit `ESCAPE '\'` and `LOWER()` on both sides, sharing the helper in `_search.py`. No virtual tables, no triggers, no schema additions. Trade-off: a substring scan over `documents.content` is linear in total content size. At CLI scale (single-user, hundreds-to-low-thousands of docs) this is fine; if document corpora grow large enough that latency hurts, swap to FTS5 just for `documents.content` (the only large blob) before scaling further.

## Invariants
- All datetimes are timezone-aware UTC.
- Schema is created via `CREATE TABLE IF NOT EXISTS` and is idempotent. There is no migration framework: schema lives in the single `_SCHEMA_SQL` DDL string and the project does not preserve existing databases across schema changes — drop the file and re-init when the schema evolves.
- `_initialized_paths` (module-private set in `connection.py`) ensures `init_schema` runs once per DB path per process.

## Key Files
- `connection.py` - Env var resolution, adapter/converter registration, `connect()` context manager, schema DDL (documents, terms, document_terms, observations, plus DFD: diagram, entity, node, container, container_membership, data_flow, data_item, flow_payload, entity_documents).
- `_search.py` - Shared `_tokenize` and `_build_text_clause` helpers used by every repo's `search()`. Owns the LIKE escape rules so they don't drift across repos.
- `models.py` - Pydantic models for the legacy domain: `DocumentCreate`/`Update`/`Document`/`DocumentSummary`, `TermCreate`/`Update`/`Term`, `ObservationCreate`/`Update`/`Observation`, plus the `ObservationType` and `ObservationStatus` literal aliases. Also includes threat assessment models: `ThreatRating`, `Tactic`, `ThreatCatalogCreate`/`ThreatCatalogEntry`, `ThreatCreate`/`ThreatUpdate`/`Threat`.
- `dfd_models.py` - Pydantic models for the DFD subdomain: `Diagram*`, node variants (`ProcessNode`, `ExternalEntityNode`, `DataStoreNode`) + discriminated `Node`/`NodeCreate`/`NodeUpdate`, container variants + discriminated `Container`/`ContainerCreate`/`ContainerUpdate`, `DataFlow*`, `DataItem*`, `FindingSeverity`, `ValidationFinding*`, plus literal aliases (`TrustLevel`, `ExternalEntityType`, `StorageType`, `PrivilegeLevel`, `Classification`, `SourceEndpoint`).
- `documents.py` - `DocumentRepository` with CRUDL plus `search()` over `title`/`author`/`content`; returns `DocumentSummary`.
- `terms.py` - `TermRepository` with CRUDL plus `link` / `unlink` / `documents_for_term` / `terms_for_document`, plus `search()` over `term`/`definition`. Reuses `_SUMMARY_COLUMNS` and `_row_to_summary` from `documents.py` for the join query.
- `observations.py` - `ObservationRepository` with CRUDL; `list()` and `search()` accept optional `observation_type` and `status` filters; `search()` text matches `content`.
- `threat_catalog.py` - `ThreatCatalogRepository`: MITRE ATT&CK reference data. `ensure_tactic(name)` (idempotent upsert), `create(data, tactic_names)` (idempotent by mitre_id, links to tactics via junction table), `get`, `exists`, `list`, `search`. Batch tactic loading via `_tactics_for_batch` avoids N+1 queries. Normalized `tactic` + `technique_tactics` junction tables.
- `threats.py` - `ThreatRepository`: formal threat assessment records. CRUDL with `rating` filter on list/search. `link_observation`/`unlink_observation` and `link_entity`/`unlink_entity` manage many-to-many junctions (`threat_observations`, `threat_entities`). Read queries batch-fetch linked ids. `threat_catalog_id` is nullable (uses DFD-style nullable update pattern).
- `diagrams.py` - `DiagramRepository` with CRUDL, `set_remote_id(diagram_id, remote_uuid)` (persists the dfd_editor-minted UUID on the row; raises `ValueError` if the id is not found), plus the `_mint_entity_id` helper imported by every other DFD repo. `search()` text matches `name`/`description`/`author` (NULL columns wrapped via `IFNULL(col, '')`).
- `dfd_export.py` - Pure adapter (Functional Core, no I/O). `to_dfd_editor_dict(diagram, nodes, containers, container_parents, flows, items, payloads_by_flow, findings=None, entity_kinds=None)` converts already-loaded tm-cli entities to the dfd_editor Diagram-shaped dict. When `findings` is provided, the payload includes a `"validation"` array; `entity_kinds` (a `{entity_id: kind_str}` map) is passed alongside to resolve per-entity GUIDs for entity-scoped findings. `payloads_by_flow` (from `DataFlowRepository.payloads_for_diagram`) drives the per-endpoint `nodeN_src_data_item_refs` arrays — without it, dfd_editor renders flows as directionless edges. `guid_for(diagram_int_id, collection, local_int_id)` produces deterministic UUIDv5s keyed on a fixed namespace (`NS_TM_DIAGRAM_PUSH`) so re-pushes preserve dfd_editor-side layout. `collection` must be one of `"nodes"`, `"containers"`, `"data_flows"`, `"data_items"`.
- `dfd_nodes.py` - `NodeRepository` (discriminated CRUDL); per-variant update enforced at runtime. `search()` text matches `name`/`description`/`assumptions`; supports `type` filter.
- `dfd_containers.py` - `ContainerRepository` (discriminated CRUDL) plus `set_parent` / `clear_parent` / `parent_of` / `children_of` for the membership graph. `search()` text matches `name`/`description`; supports `type` filter.
- `dfd_flows.py` - `DataFlowRepository` (CRUDL with canonical-order create) plus `add_payload` / `remove_payload` / `payload_for_flow` / `payloads_for_diagram` (bulk lookup → `{flow_id: {1: [item_id, ...], 2: [...]}}` for export) / `flows_for_data_item`. `search()` text matches `name`/`protocol`.
- `dfd_items.py` - `DataItemRepository` with CRUDL; nullable `parent_node_id` clearable via update. `search()` text matches `identifier`/`name`/`description`; supports `classification` and `parent_node_id` filters.
- `dfd_findings.py` - `ValidationFindingRepository` with CRUDL, `search(diagram_id, text, *, severity, source, ...)` (text matches `message`/`code`; supports `severity` and `source` filters), `clear(diagram_id, *, source)` (bulk delete by diagram, optionally filtered to a single source; returns count), and `for_diagram(diagram_id)` (unbounded read, used by `diagrams.py` push to populate the export payload).
- `entity_documents.py` - `EntityDocumentRepository`: many-to-many junction between any DFD entity (all four kinds) and `documents`. `link` / `unlink` / `documents_for_entity`, plus per-kind reverse lookups (`nodes_for_document`, `containers_for_document`, `flows_for_document`, `items_for_document`). Reuses `_row_to_*` helpers from each kind repo.
- `entity_observations.py` - `EntityObservationRepository`: many-to-many junction between any DFD entity (all four kinds) and `observations`. `link` / `unlink` / `observations_for_entity` (returns enriched `Observation` rows with `*_ids` populated), plus per-kind reverse lookups (`nodes_for_observation`, `containers_for_observation`, `flows_for_observation`, `items_for_observation`). `linked_ids_by_kind(observation_id)` and `linked_ids_by_kind_for(observation_ids)` return `LinkedIds` TypedDicts bucketing entity ids by kind. Reuses `_row_to_*` helpers from each kind repo, plus `_row_to_observation` and `_OBSERVATION_COLUMNS` from `observations.py`. The enrichment loop (`_attach_linked_ids`) lives in `observations.py`; `entity_observations.py` calls it via a local import to avoid a module-level circular dependency.
- `__init__.py` - Public re-exports for both subdomains.

## Gotchas
- `register_adapter` / `register_converter` are **process-global**, applied as a side effect of importing `tm_cli.db.connection`. This is fine for the CLI but be aware in tests or notebooks that share the process.
- `DocumentRepository.update` always bumps `last_imported`, even when the patch has no fields set — touching a doc is a meaningful "re-imported, no changes" event. `TermRepository.update` and `ObservationRepository.update` follow the same convention for `last_updated`.
- `list()` on documents returns `DocumentSummary`, not `Document`. Don't expect `.content` on those.
- `document_terms` is the project's first FK relationship and has `ON DELETE CASCADE` on both sides. Be aware when running ad-hoc DELETEs against `documents` or `terms` — links go with them. `PRAGMA foreign_keys = ON` is set in `connect()`; cascades only fire there, not in raw `sqlite3` shells where the pragma is off by default.
- `terms.py` imports `_SUMMARY_COLUMNS` and `_row_to_summary` from `documents.py`. They're module-private in the package sense but treated as a stable in-package contract — change the document summary shape and both files need updates.
- Adding a new value to `ObservationType` or `ObservationStatus` requires updating BOTH the Pydantic `Literal` in `models.py` AND the corresponding SQL `CHECK` constraint in `connection.py`. The CHECK is part of the table definition — adding a value to the literal alone will start raising `sqlite3.IntegrityError` at write time.
- `TM_DB_PATH` is required and there is no default — `connect()` raises `RuntimeError` if unset.

## DFD subdomain

The DFD layer stores structured threat-model diagrams: `diagram` (aggregate root) -> `entity` (master id table) -> `node` / `container` / `data_flow` / `data_item`, plus the `container_membership` and `flow_payload` link tables.

### Contracts
- **Composition cascade**: deleting a `diagram` cascades to `entity` (via `entity.diagram_id` FK) and from `entity` to all four kind tables (their PKs are FKs to `entity.id`). All link tables (`container_membership`, `flow_payload`) cascade off their endpoints. `validation_finding` rows cascade on both `diagram_id` (diagram delete drops all its findings) and `entity_id` (entity delete drops any findings pinned to that entity; `entity_id` is nullable so diagram-level findings without an entity are unaffected). Deleting one diagram drops everything in it.
- **Cross-table id uniqueness**: `entity` is the master id table. Every `node` / `container` / `data_flow` / `data_item` row has its PK = `entity.id`, so ids are globally unique within the DB across all four kinds. Repositories mint ids via a 2-step insert: `INSERT INTO entity` then `INSERT INTO <kind>` with the new id.
- **Discriminated nodes / containers**: one SQL table per concept (`node`, `container`) with sparse per-variant columns. The `type` column is the discriminator; per-variant required-column closure is enforced by a multi-clause SQL `CHECK`. Pydantic uses `Annotated[A | B | C, Field(discriminator="type")]`. `NodeRepository.update` requires the patch class to match the row's current type — type changes are not supported on update (delete & recreate). Same for `ContainerRepository.update`.
- **Two-layer enum defense**: `TrustLevel`, `ExternalEntityType`, `StorageType`, `PrivilegeLevel`, `Classification`, `SourceEndpoint`, plus the node/container `type` discriminators are all enforced at both layers (Pydantic `Literal` and SQL `CHECK`).
- **`process` node `assumptions`**: stored as JSON-encoded TEXT with a `CHECK (assumptions IS NULL OR json_valid(assumptions))` constraint. Repo does explicit `json.dumps`/`json.loads`. (Requires SQLite 3.38+; verified at 3.53 locally.)
- **Canonical flow endpoint ordering**: `data_flow.node1_id < data_flow.node2_id` is enforced at SQL (`CHECK`). The repository canonicalizes on create (`a, b = sorted([n1, n2])`). Self-loops are rejected by the same CHECK and explicitly in the repository. **Endpoints are not updatable** — `DataFlowUpdate` omits node1/node2; callers delete & recreate to swap endpoints.
- **Container hierarchy**: `container_membership.child_id` is PK, so each child has at most one parent (the graph is a forest). Acyclicity, kind restriction (children must be nodes or containers), and same-diagram requirement are application-enforced in `ContainerRepository.set_parent`. SQL only enforces `child_id != parent_id`.
- **Diagram-scope checks** for flow endpoints, payload references (`add_payload`), container membership, and `data_item.parent_node_id` are application-enforced. The endpoints themselves are FK'd to their respective tables but the same-diagram restriction is not structural.
- **`data_item.parent_node_id`** is nullable; on parent node delete, `ON DELETE SET NULL` clears it. To clear via the repo, call `update(id, DataItemUpdate(parent_node_id=None))` — the repo recognizes the explicit `None` (see "nullable update" below).
- **`flow_payload`**: composite PK `(flow_id, data_item_id, source_endpoint)` lets the same data_item appear at both endpoints (two rows). `add_payload` uses `INSERT OR IGNORE` for idempotency, mirroring `terms.py`'s `link`.
- **Entity ↔ Document links** (`entity_documents`): any of the four DFD kinds may be linked to any number of `documents` rows (and vice versa). Composite PK on `(entity_id, document_id)` makes link insertion idempotent via `INSERT OR IGNORE`. Both FKs cascade-delete: removing a document drops its links; removing a DFD entity (always via `entity`) drops its links; removing a `diagram` drops everything by transitive cascade. The single junction across all kinds is sound only because every kind row's PK is `entity.id` (minted via `_mint_entity_id`).
- **Entity ↔ Observation links** (`entity_observations`): mirrors `entity_documents`. Same cascade-delete behavior: deleting an observation removes its links; deleting a DFD entity (via `entity`) removes its links; deleting a diagram cascades transitively. `Observation` read model carries four `list[int]` fields (`node_ids`, `container_ids`, `flow_ids`, `data_item_ids`) populated by `EntityObservationRepository.linked_ids_by_kind` (single-row) or `linked_ids_by_kind_for` (batched, no N+1). `ObservationRepository.list()` and `search()` use the batched helper; `get()` uses the single-row helper. All four lists default to `[]` (Pydantic `Field(default_factory=list)`).

### Repositories (re-exported from `tm_cli.db`)
`DiagramRepository`, `NodeRepository`, `ContainerRepository`, `DataFlowRepository`, `DataItemRepository`, `EntityDocumentRepository`, `EntityObservationRepository`, `ValidationFindingRepository`. Each takes an open `sqlite3.Connection`. Node and Container repos take the discriminated union for `create` (one method per concept, dispatch on type internally). Per-variant `*Update` classes for nodes/containers; `update` raises `ValueError` if the patch type doesn't match the row's variant. `DiagramRepository` also exposes `set_remote_id(diagram_id, remote_uuid)` — not part of the CRUDL pattern but called by `tm diagram push` after the server mints a UUID. `ValidationFindingRepository` exposes CRUDL + `search(diagram_id, text, *, severity, source, limit, offset)` + `clear(diagram_id, *, source)` (bulk delete, returns count) + `for_diagram(diagram_id)` (unbounded, used by the push path).

### Gotchas
- **`ValidationFindingRepository.create` validates `entity_id` membership**: if `entity_id` is supplied, the repo queries `entity.diagram_id` and raises `ValueError` if the entity doesn't exist or belongs to a different diagram. This check is application-enforced — the SQL FK on `entity_id` only enforces existence, not diagram-scope consistency.
- **Direct `DELETE FROM node`/etc. leaves orphan `entity` rows.** The FK is from kind table -> `entity`, not the reverse. Repos always delete via `DELETE FROM entity WHERE id = ? AND kind = '...'` so the kind row goes by cascade. If you write ad-hoc SQL, do the same.
- **Acyclicity is application-enforced** in `set_parent` (walks the parent's ancestor chain and rejects if `child_id` appears). Single-process CLI, so the racy multi-writer case isn't a concern today.
- **Container membership kind-restriction is application-enforced**: `child_id` FK targets `entity.id` which holds all kinds. The repo's `set_parent` rejects flow / data_item ids; raw inserts can violate this.
- **Nullable update divergence**: existing repos (`documents.py`, `terms.py`, `observations.py`) use `if field in patch_data and patch_data[field] is not None` — that pattern conflates "not set in patch" with "explicitly set to None" and prevents clearing nullable fields. The DFD repos drop the `is not None` guard for nullable fields (`DataItemRepository` for `parent_node_id`, `DiagramRepository` for `name`/`description`/`author`) and rely on `model_dump(exclude_unset=True)` alone, so callers can clear via explicit `None`.
- **Adding a new variant or enum value** requires touching: the Pydantic `Literal` (or new variant class + union) in `dfd_models.py`, the SQL `CHECK` constraints in `connection.py`, and any per-variant dispatch (`_row_to_node`, `NodeRepository.create`/`update`).
- **`DataFlowUpdate` cannot change endpoints**. Update model omits `node1_id`/`node2_id`; deliberate to avoid re-canonicalizing and re-validating same-diagram on update.
- **`identifier` on `data_item` is not unique.** Spec doesn't require it; add UNIQUE later if needed.
