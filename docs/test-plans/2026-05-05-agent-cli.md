## Prerequisites

- Python 3.11+, `uv`, `make`
- `make install-deps` completed
- `make lint` and `make test` pass on the working tree
- Set `TM_DB_PATH` to a fresh sqlite file (see `.env.example`)
- Initialize schema: invoke any command once to ensure schema is created (or run a fixture seed)
- Use a real terminal for TTY-affected steps; pipe to `cat` to test piped output

## Phase 2: Output Format on a Real TTY (AC4.3 cross-check)

The unit tests use `--no-json` because `CliRunner` lacks a TTY. Verify that auto-detection works on a real terminal.

| Step | Action | Expected |
|---|---|---|
| 2.1 | `tm document create --title "Test" --author A --content "Body"` (real terminal, no pipe) | Output is indented JSON (newlines, two-space indent visible) |
| 2.2 | `tm document create --title "T2" --author A --content "B2" \| cat` | Output is single-line compact JSON; no leading/trailing whitespace |
| 2.3 | `tm document list` (no pipe) | Each row is indented JSON (multi-line per row) |
| 2.4 | `tm document list \| cat` | NDJSON: one compact JSON object per line |

This is the strongest smoke test that the TTY auto-detection in `_default_json_mode()` works in production environments where real `isatty()` is involved.

## End-to-End: Realistic Threat Modeling Session

**Purpose:** Validates that an agent can complete a non-trivial workflow using only `--help` and `tm commands --json` for discovery.

**Scenario:** Model a simple web app with a frontend, backend, and database; flag PII handling.

Steps:
1. `tm diagram create --name "webapp-tm"` — capture `$DID`
2. `tm node create process --diagram-id $DID --name Frontend --description "SPA" --trust-level public` — capture `$FE`
3. `tm node create process --diagram-id $DID --name Backend --description "API server" --trust-level authenticated` — capture `$BE`
4. `tm node create data-store --diagram-id $DID --name UserDB --description "Postgres users" --storage-type database --contains-pii --encryption-at-rest` — capture `$DB`
5. `tm flow create --diagram-id $DID --node1-id $FE --node2-id $BE --name "user-actions" --protocol https --authenticated --encrypted`
6. `tm flow create --diagram-id $DID --node1-id $BE --node2-id $DB --name "user-queries" --protocol postgres --authenticated --encrypted`
7. `tm data-item create --diagram-id $DID --identifier "user.email" --name Email --description "User email" --classification pii --parent-node-id $DB`
8. `tm flow add-payload <user-queries-flow-id> --data-item <email-item-id> --endpoint 1`
9. `tm observation create --observation-type todo --status open --content "Encrypt email at rest"`
10. `tm document create --title "Threat model" --author auditor --content "PII handling notes"` — capture `$DOC`
11. `tm node link-document $BE $DOC`
12. `tm document list-nodes $DOC` — confirms backend appears
13. `tm flow list-payloads <user-queries-flow-id>` — confirms email payload appears
14. `tm observation search "encrypt" --status open` — finds the observation

**Expected:** All commands exit 0; final state reflects the modeled system. Each entity id is a string; ids round-trip correctly across commands. Help-text-only navigation suffices (no source-code lookup required).

## Human Verification Required

Per the test-requirements.md "Human verification" section, no AC formally requires a manual procedure. The closest call is **AC10.5 snapshot drift review**: when `pytest --snapshot-update` is run, a human MUST diff `tests/cli/__snapshots__/test_introspection.ambr` against the previous version and confirm the change is intentional before committing — the snapshot is the agent contract.

| Concern | Why Manual | Steps |
|---|---|---|
| AC10.5 snapshot review | Drift is intentional only when grouped with a deliberate API change | When you see `test_commands_json_golden_snapshot` fail, run `git diff tests/cli/__snapshots__/test_introspection.ambr`. Confirm every changed line corresponds to a deliberate rename, addition, or removal in the implementation diff. Reject if drift is incidental. |
| AC5.5 / AC5.6 production reachability | Plan documents these as unit-only because the surface is structurally unreachable / portably awkward | If a future change makes either reachable end-to-end, replace the unit-only entry with an integration test |
