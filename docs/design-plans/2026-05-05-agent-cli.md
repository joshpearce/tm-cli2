# Agent CLI Design

## Summary

The design builds a `tm` CLI as a thin Click layer over the existing `src/tm_cli/db/` repositories, which are already complete. Each command opens a connection, instantiates one repository, calls one method, and hands the result to a single output helper. There's no business logic in the CLI itself: validation lives in Pydantic models, constraint enforcement lives in SQLite, and domain rules live in the repositories. The CLI's job is to translate flags to repo calls and translate results (or exceptions) to structured JSON output.

The design is agent-first throughout. All output defaults to JSON (NDJSON for lists, a single object for point reads), structured errors always go to stderr with stable exit codes, and the output format auto-detects TTY vs. pipe without any flags. The default-diagram fallback — where DFD entity commands silently resolve or create a diagram named "default" — keeps the common single-diagram workflow to a single command, while the hidden `--diagram-id` flag lets curious agents discover and override it via `tm commands --json`. Polymorphic types (Node and Container) use explicit-type subcommands — `tm node create process`, `tm node update data-store` — rather than a shared create command with a type discriminator flag, so each subcommand exposes only the fields that belong to its variant and type mismatches are caught at parse time or on the first repo call.

## Definition of Done

**In scope (deliverables):**
- Full `tm` CLI surface under `src/tm_cli/cli/` exposing CRUD + `search` + relationship operations for every entity in the existing db layer: Documents, Terms, Observations, Diagrams, Nodes (3 variants: process, external-entity, data-store), Containers (variants), DataFlows, DataItems, plus the four junctions (`document_terms`, `container_membership`, `flow_payload`, `entity_documents`).
- Conformance to `docs/agent-cli-design.md`: `tm <noun> <verb>` shape; JSON-by-default output; structured stderr errors with stable exit codes (0/1/2/3/4); long flags only in the public contract; JSON stdin for bulk create/update with output mirroring input shape; `--if-not-exists` creates; idempotent deletes; `--dry-run` on mutations; default-lean list output (large text fields excluded); consistent pagination/filter/sort across all `list`/`search` commands.
- Per-entity `search` subcommand (whitespace-tokenized text plus repeatable filter flags plus pagination), surfacing each repository's `search()` method.
- Polymorphic Node and Container use explicit-type subcommands for **both** create and update (e.g., `tm node create process …`, `tm node update process <id> …`).
- Introspection: `tm schema [<entity>]` (derived from Pydantic `model_json_schema()`) and `tm commands --json` (machine-readable command tree from Click introspection).
- Tests: golden-file JSON output tests and golden-file `--help` text tests for every command; unit tests for the error-shape converter and introspection commands.
- Phased plan: global CLI scaffolding -> legacy-domain entity commands -> DFD entity commands -> junction/relationship commands -> introspection commands -> tests-as-contract.

**Out of scope:**
- Higher-level workflow commands (no `tm import`, no `tm diff`, no multi-entity transactional bundles).
- Agent workflow state in the DB (no "processed" flags, no validation queues).
- Database schema changes (the persistence layer is complete).
- Extraction or LLM logic that produces the rows the CLI manipulates.

## Acceptance Criteria

### agent-cli.AC1: Standard CRUDL behaviors (universal across entities)
- **agent-cli.AC1.1 Success:** `list` returns all rows for an entity as NDJSON when stdout is piped (one JSON object per line).
- **agent-cli.AC1.2 Success:** `get` returns the full model for an existing id (including server-set fields like `last_imported`).
- **agent-cli.AC1.3 Success:** `create` with valid flags returns the new row, including the synthesized id (string-quoted) and any server-managed timestamps.
- **agent-cli.AC1.4 Success:** `update` with a valid patch returns the resulting row (full object, not `{"ok": true}`).
- **agent-cli.AC1.5 Failure:** `get` of a missing id exits 2 with `error.code = "not_found"`.
- **agent-cli.AC1.6 Failure:** `update` of a missing id exits 2 with `error.code = "not_found"`.
- **agent-cli.AC1.7 Failure:** `create` with an invalid enum value (e.g., `--observation-type=bogus`) exits 1 at the Click parser with a Choice error.
- **agent-cli.AC1.8 Edge:** `list --limit N` where `N` exceeds the row count returns all rows with no `_pagination` footer.

### agent-cli.AC2: Search
- **agent-cli.AC2.1 Success:** `search "X"` matches case-insensitively across all searchable text columns for the entity (per the repo's `search()` columns).
- **agent-cli.AC2.2 Success:** Multi-token text (`search "foo bar"`) AND-combines tokens; each token must match at least one searchable column.
- **agent-cli.AC2.3 Success:** `tm observation search "todo" --observation-type=todo --status=open` AND-combines text and filters.
- **agent-cli.AC2.4 Success:** `tm node search "..." --type=process` filters results to the named variant.
- **agent-cli.AC2.5 Success:** `tm data-item search` with `--classification` and `--parent-node-id` filters returns the AND of those constraints.
- **agent-cli.AC2.6 Success:** `tm flow search "X"` matches against `name` and `protocol` columns.
- **agent-cli.AC2.7 Edge:** `search` with empty text plus filters returns the same shape as `list` with those filters.

### agent-cli.AC3: Junctions
- **agent-cli.AC3.1 Success:** `tm document link-term <doc-id> <term-id>` creates the link; subsequent `tm document list-terms <doc-id>` includes the term.
- **agent-cli.AC3.2 Success:** Re-linking the same pair returns `{"linked": false, "reason": "already_linked"}` and exits 0.
- **agent-cli.AC3.3 Success:** `tm document unlink-term` removes the link; the term no longer appears in `list-terms`.
- **agent-cli.AC3.4 Success:** `tm container set-parent` followed by `tm container parent-of` round-trips; `tm container list-children` includes the new child with a `type` discriminator.
- **agent-cli.AC3.5 Failure:** `set-parent` across diagrams exits 1 with a hint naming the cross-diagram constraint.
- **agent-cli.AC3.6 Failure:** `set-parent` that would create a cycle exits 1 with a cycle-detected hint.
- **agent-cli.AC3.7 Success:** `tm flow add-payload <flow-id> --data-item ID --endpoint 1` plus a second call with `--endpoint 2` round-trips through `tm flow list-payloads`; `--endpoint` filter on list returns just the matching payloads.
- **agent-cli.AC3.8 Failure:** `tm flow add-payload --endpoint=3` rejected by Click's `Choice` at parse (exit 1).
- **agent-cli.AC3.9 Success:** `link-document` on each of the four DFD entities (`tm node`, `tm container`, `tm flow`, `tm data-item`) works; `list-documents` on the same entity reflects the link.
- **agent-cli.AC3.10 Success:** `tm document list-nodes / list-containers / list-flows / list-items` each return the entities of that kind linked to the document.

### agent-cli.AC4: Output format
- **agent-cli.AC4.1 Success:** Piped `list` and `search` output is NDJSON (no surrounding `[`/`]`); each row is one parseable JSON object.
- **agent-cli.AC4.2 Success:** Piped `get` / `create` / `update` output is a single compact JSON object on stdout.
- **agent-cli.AC4.3 Success:** When stdout is a TTY, all JSON output is indented with `indent=2`.
- **agent-cli.AC4.4 Success:** Integer id fields serialize as JSON strings (e.g., `"id": "5"`, not `5`).
- **agent-cli.AC4.5 Success:** Pagination footer `{"_pagination": {"next_offset": N, "returned": N}}` is the final NDJSON line when `len(rows) == limit`.
- **agent-cli.AC4.6 Success:** `--json id,name` projects only the requested fields on both `list` and `get`.

### agent-cli.AC5: Errors and exit codes
- **agent-cli.AC5.1 Success:** `pydantic.ValidationError` from a repo call → exit 1, `error.code = "user_error"`.
- **agent-cli.AC5.2 Success:** Repo returning `None` from `get`/`update` → exit 2, `error.code = "not_found"`.
- **agent-cli.AC5.3 Success:** UNIQUE constraint violation (e.g., duplicate `Term.term`) → exit 3, `error.constraint = "unique"`.
- **agent-cli.AC5.4 Success:** FOREIGN KEY violation → exit 3, `error.constraint = "foreign_key"`.
- **agent-cli.AC5.5 Success:** CHECK violation → exit 3, `error.constraint = "check"`.
- **agent-cli.AC5.6 Success:** `OSError` / `PermissionError` (e.g., DB path unwritable) → exit 4, `error.code = "system_error"`.
- **agent-cli.AC5.7 Success:** Error JSON is written to stderr; stdout is either empty or remains a parseable JSON document.

### agent-cli.AC6: Idempotency and --dry-run
- **agent-cli.AC6.1 Success:** `tm term create --if-not-exists --term foo --definition bar` with `foo` already present returns the existing row with `{"created": false, ...}` and exits 0.
- **agent-cli.AC6.2 Success:** `delete <existing-id>` returns `{"deleted": true, "id": "..."}` and exits 0.
- **agent-cli.AC6.3 Success:** `delete <missing-id>` returns `{"deleted": false, "id": "...", "reason": "not_found"}` and exits 0.
- **agent-cli.AC6.4 Success:** `create --dry-run` returns `{"dry_run": true, "would_create": {...}}` and writes nothing to the DB.
- **agent-cli.AC6.5 Success:** `update --dry-run` returns `{"dry_run": true, "would_update": {...}}` and modifies nothing.

### agent-cli.AC7: Stdin bulk
- **agent-cli.AC7.1 Success:** `tm document create --stdin` with a single JSON object on stdin creates one row and returns one object.
- **agent-cli.AC7.2 Success:** `tm document create --stdin` with a JSON array creates N rows in input order and returns an array of N objects in the same order, all in a single connection.
- **agent-cli.AC7.3 Failure:** A single invalid item in an input array rolls back the whole batch; the error payload includes the failing item's array index.
- **agent-cli.AC7.4 Failure:** `--stdin` combined with any `--field` flag is rejected at the Click parser (mutually exclusive).

### agent-cli.AC8: Polymorphism (Node, Container)
- **agent-cli.AC8.1 Success:** `tm node create process|external-entity|data-store` dispatches to the correct variant; each subcommand exposes only its variant's fields as flags.
- **agent-cli.AC8.2 Success:** `tm node update process <id>` against a process row updates the row and returns the updated process node.
- **agent-cli.AC8.3 Failure:** `tm node update process <data-store-id>` exits 1 with `error.code = "user_error"` and a hint identifying the actual row type.
- **agent-cli.AC8.4 Success:** `tm container create trust-boundary|container` dispatches correctly; matching `update` subcommands enforce the type-match rule.
- **agent-cli.AC8.5 Success:** `--type` filter on `list` and `search` restricts results to the named variant.

### agent-cli.AC9: Default-diagram fallback
- **agent-cli.AC9.1 Success:** A DFD `create` command without `--diagram-id` creates a diagram named "default" when none exists, then creates the entity in it; the response includes the resolved `diagram_id`.
- **agent-cli.AC9.2 Success:** DFD `list` / `search` without `--diagram-id` and no default diagram in the DB returns empty NDJSON (no implicit creation on read).
- **agent-cli.AC9.3 Success:** DFD `list` / `search` without `--diagram-id` uses the default diagram's id when one exists.
- **agent-cli.AC9.4 Success:** `--diagram-id` does not appear in any DFD command's `--help` output.
- **agent-cli.AC9.5 Success:** `tm commands --json` emits the `--diagram-id` option with `"hidden": true` so curious agents can discover it.

### agent-cli.AC10: Introspection
- **agent-cli.AC10.1 Success:** `tm schema document` returns the JSON Schema for the read model plus `DocumentCreate` and `DocumentUpdate`.
- **agent-cli.AC10.2 Success:** `tm schema` (no argument) lists available entity names.
- **agent-cli.AC10.3 Success:** `tm schema --all` returns one document keyed by entity name.
- **agent-cli.AC10.4 Success:** `tm commands --json` walks the full command tree; every leaf has `options` and `arguments` keys (possibly empty arrays).
- **agent-cli.AC10.5 Success:** `tm commands --json` output is pinned by a golden snapshot; drift requires explicit snapshot update.

### agent-cli.AC11: Entity-specific invariants
- **agent-cli.AC11.1 Success:** `tm flow create --node1-id 5 --node2-id 3 ...` produces a row with `node1_id=3, node2_id=5` (canonicalized transparently by the repo).
- **agent-cli.AC11.2 Failure:** `tm flow create --node1-id 5 --node2-id 5 ...` exits 1 with a self-loop hint.
- **agent-cli.AC11.3 Constraint:** `tm flow update --help` shows no `--node1-id` or `--node2-id` flags; `tm commands --json` output for `flow update` likewise omits them.
- **agent-cli.AC11.4 Success:** `tm data-item update <id> --parent-node-id ""` (or the equivalent stdin-cleared form) sets the row's `parent_node_id` to NULL.

## Glossary

- **Data flow diagram (DFD)**: a diagram that shows how data moves between processes, external entities, and data stores. The four DFD entity types in this design are Node, Container, DataFlow, and DataItem.
- **Document**: a source artifact (threat model report, design doc, RFC) stored as free text. Documents can be linked to Terms, Observations, and DFD entities via junction tables.
- **Term**: a glossary entry with a natural-key field (`term`) that the CLI uses for `--if-not-exists` idempotency.
- **Observation**: a finding, assumption, or to-do attached to a threat model. Has `observation_type` and `status` enum fields.
- **Diagram**: a named DFD canvas. All DFD entities belong to exactly one diagram.
- **Node**: a polymorphic DFD element with three variants — `process`, `external_entity`, and `data_store`. Variants share a table but have different fields.
- **Container**: a polymorphic grouping element with two variants — `trust_boundary` and `container`. Can hold Nodes and other Containers.
- **DataFlow**: a directed connection between two Nodes. Endpoints are canonically ordered (lower id first) by the repository and are immutable after creation.
- **DataItem**: a piece of data that can be associated with a Node (via `parent_node_id`) and attached to a DataFlow as a payload.
- **Junction table**: a database table that records many-to-many relationships between two entities. This design has four: `document_terms`, `container_membership`, `flow_payload`, and `entity_documents`.
- **`document_terms`**: links Documents to Terms in either direction.
- **`container_membership`**: records parent–child relationships between Containers and their Node or Container children within a single diagram.
- **`flow_payload`**: associates DataItems with a DataFlow at a specific endpoint (1 or 2).
- **`entity_documents`**: links any of the four DFD entity types to Documents.
- **Pydantic discriminated union**: a Pydantic v2 pattern where a single annotated type resolves to one of several model classes based on a `type` discriminator field. Used here for Node and Container so the repository and CLI subcommand generation both key off the same Python type structure.
- **NDJSON (newline-delimited JSON)**: a format where each line is a self-contained JSON object. Used for `list` and `search` output so consumers can stream or process rows incrementally.
- **Click `result_callback`**: a Click mechanism that runs after a command group's invocation completes (or raises). Used here to catch uncaught exceptions and map them to structured `TmError` payloads with stable exit codes.
- **Syrupy**: a pytest plugin for snapshot ("golden file") testing. Assertions fail when output drifts from a stored snapshot; the developer must explicitly run `--snapshot-update` to bless a change.
- **Default-diagram fallback**: the behavior where DFD `create` commands without `--diagram-id` look up (or create) a diagram named "default", making single-diagram workflows require no diagram management. `--diagram-id` is hidden from `--help` but visible in `tm commands --json`.
- **`tm commands --json`**: the introspection command that emits the full Click command tree as a JSON document, including hidden options. Intended as the machine-readable alternative to reading `--help` output.

## Architecture

The CLI is a thin Click layer over the existing repositories in `src/tm_cli/db/`. Each Click command opens a connection via `connect()`, instantiates the relevant repository, calls one method, and emits the result through a single output helper. Errors are translated by a root-level result callback. Nothing else.

### Module layout

```
src/tm_cli/
├── main.py                  -- root CLI group; loads .env; registers subgroups
└── cli/
    ├── __init__.py
    ├── _output.py           -- emit(); JSON encoder with stringified IDs
    ├── _errors.py           -- TmError hierarchy + result_callback
    ├── _options.py          -- shared decorators + resolve_default_diagram_id
    ├── _stdin.py            -- read_json_stdin() for --stdin bulk
    ├── _introspection.py    -- tm schema and tm commands
    ├── documents.py         -- tm document ...
    ├── terms.py             -- tm term ...
    ├── observations.py      -- tm observation ...
    ├── diagrams.py          -- tm diagram ...
    ├── nodes.py             -- tm node ... (polymorphic)
    ├── containers.py        -- tm container ... (polymorphic)
    ├── flows.py             -- tm flow ...
    └── items.py             -- tm data-item ...
```

One module per entity. Junction commands live on the entity that's the natural subject (e.g., `tm document link-term` on `documents.py`, `tm node set-parent` on `nodes.py`). Shared helpers are underscore-prefixed module-private files; entity modules import from them.

### Output

The root `cli` group declares `--json/--no-json`. Default is `True` when `sys.stdout.isatty()` is False (piped or agent-driven), `False` when a TTY (humans). Resolved value is stored in `ctx.obj['json']` and read by every command.

`_output.emit(ctx, payload, *, list_mode=False)` is the single write path:

```python
def emit(ctx: click.Context, payload: object, *, list_mode: bool = False) -> None:
    """Emit payload to stdout. list_mode=True writes NDJSON, one row per line."""
```

Behavior:
- `list_mode=False`: one JSON object (compact when piped, `indent=2` when TTY).
- `list_mode=True`: NDJSON, one row per line, terminated with a `_pagination` footer line when `len(rows) == limit`.
- IDs serialized as strings via a custom `json.JSONEncoder` subclass that wraps Pydantic `model_dump(mode='json')` output and post-processes integer fields named `id`, `*_id`. Datetimes serialize to ISO-8601 UTC (Pydantic default).

### Errors

```python
class TmError(click.ClickException):
    exit_code: int
    def to_payload(self) -> dict: ...

class UserError(TmError):       # exit 1
class NotFoundError(TmError):   # exit 2
class ConstraintError(TmError): # exit 3
class SystemError(TmError):     # exit 4
```

A `result_callback` registered on the root group catches uncaught exceptions and maps them:

| Source exception | Translated to | Exit |
|---|---|---|
| `pydantic.ValidationError` | `UserError` | 1 |
| Repo `get()` / `update()` returning `None` | `NotFoundError` | 2 |
| `sqlite3.IntegrityError` (UNIQUE / FK / CHECK) | `ConstraintError` (constraint kind extracted from message) | 3 |
| `ValueError` from repo (type mismatch on update, self-loop, cross-diagram) | `UserError` | 1 |
| `OSError` / `PermissionError` | `SystemError` | 4 |

Error JSON on stderr:

```json
{"error": {"code": "constraint_violation", "constraint": "unique", "message": "...", "hint": "...", "input": {...}}}
```

`hint` is populated when the mapper has actionable advice (e.g., for UNIQUE on `Term.term`, the hint is "use `tm term create --if-not-exists` to be idempotent"). The `input` field echoes the offending payload — agents whose context has moved on can recover ground truth.

### Stdin bulk input

`--stdin` is an explicit flag on every `create` and `update`. Without it, named flags are required. With it, named flags are forbidden (Click `mutually_exclusive`). `_stdin.read_json_stdin()` parses the body:

- Object → single mutation, returns one object.
- Array → batched in a single `connect()` block, returns an array of objects in input order.
- Output shape always mirrors input shape.

A failed item in an array does not partially commit — the connection's exception path rolls everything back. Error payload echoes the failing input plus its array index.

### Default-diagram fallback

DFD entities (Node, Container, DataFlow, DataItem) require a `diagram_id` at the repo. The CLI exposes `--diagram-id` as `hidden=True` so it doesn't show in `--help`. `_options.resolve_default_diagram_id(conn, explicit_id, *, create_if_missing)` resolves the value:

1. If `explicit_id` is set, use it (after a quick existence check; missing → `NotFoundError`).
2. Otherwise scan `DiagramRepository.list()` for a row named `"default"`, lowest id wins on tie.
3. If none found:
   - On **create** commands (`create_if_missing=True`): create one with `DiagramCreate(name="default")` and return its id.
   - On **list** / **search** commands (`create_if_missing=False`): return `None`. Caller skips the repo call and emits an empty NDJSON list.

`update`, `delete`, and `get` for DFD entities are unaffected — they take the entity id directly and the repo doesn't need a diagram_id. `tm diagram` commands manage diagrams themselves and don't inherit the hidden flag.

Known v1 quirk: a user creating an explicit diagram named "default" will silently take ownership of all default-diagram traffic. The doc captures this; future multi-diagram work can surface the flag (`hidden=False`) and add a `tm config set-default-diagram` command.

### Per-entity command surface

Every entity exposes the same six verbs:

```
tm <noun> list      [--diagram-id ID]* [--limit N] [--offset N] [--sort F] [--order asc|desc] [--filter K=V]... [--json fields]
tm <noun> get       <id> [--json fields]
tm <noun> create    [--field VALUE]... | --stdin     [--if-not-exists] [--dry-run]
tm <noun> update    <id> [--field VALUE]... | --stdin   [--dry-run]
tm <noun> delete    <id> [--yes] [--dry-run]
tm <noun> search    <text> [<same flags as list>]
```

`*` = present on DFD entities, hidden, with default-diagram fallback.

Per-entity filter flags derive from each repository's `search()` signature:

| Entity | Filter flags |
|---|---|
| `tm observation` | `--observation-type` (Choice), `--status` (Choice) on list and search |
| `tm node` | `--type` (Choice: process, external_entity, data_store) on list and search |
| `tm container` | `--type` (Choice: trust_boundary, container) on list and search |
| `tm data-item` | `--classification` (Choice), `--parent-node-id` (INT) on search; `list` routes through `repo.search(text=None, **filters)` for parity |

Defaults: `--limit 50`, `--sort id`, `--order asc`. The `_pagination` footer fires when `len(rows) == limit`.

`tm document list` and `tm document search` return `DocumentSummary` (no `content`). `get` returns the full model. `--json fields` projects further on every list and get.

Idempotency:

- `delete` always exits 0. Returns `{"deleted": true, "id": "..."}` if the row existed, `{"deleted": false, "id": "...", "reason": "not_found"}` otherwise.
- `create --if-not-exists`: for `Term`, uses `TermRepository.get_by_term()` for the natural-key lookup. For other entities the flag is accepted but no-ops to PK-only idempotency (which is meaningless on creates that mint new ids).
- `create` and `update` always return the resulting object, not `{"ok": true}`.
- `--dry-run` validates inputs through Pydantic and runs all pre-flight checks but does not write. Returns `{"dry_run": true, "would_create": {...}}` or `would_update` / `would_delete`.

Polymorphic create/update for Node and Container use explicit-type subcommands. Per-variant subcommands are generated by iterating each Pydantic variant's `model_fields`:

```
tm node create process       --name ... --description ... --trust-level ... [--assumption JSON]...
tm node create external-entity --name ... --description ... --entity-type ... [--out-of-scope/--no-out-of-scope]
tm node create data-store    --name ... --description ... --storage-type ... --contains-pii/--no-contains-pii --encryption-at-rest/--no-encryption-at-rest
tm node update <variant>     <id> ... -- variant must match the row's current type
```

Boolean fields render as `--flag/--no-flag` pairs. List fields like `assumptions` accept repeatable flags (`--assumption "..."` × N). The same pattern applies to `tm container create trust-boundary | container` and matching update.

### Junction commands

```
document_terms (TermRepository.link/unlink/...):
  tm document link-term     <doc-id> <term-id>
  tm document unlink-term   <doc-id> <term-id>
  tm document list-terms    <doc-id> [<list flags>]
  tm term     list-documents <term-id> [<list flags>]

container_membership (ContainerRepository.set_parent/...):
  tm node      set-parent    <node-id> <container-id>
  tm node      clear-parent  <node-id>
  tm node      parent-of     <node-id>
  tm container set-parent    <container-id> <parent-id>
  tm container clear-parent  <container-id>
  tm container parent-of     <container-id>
  tm container list-children <container-id>     -- mixed Node|Container with type discriminator

flow_payload (DataFlowRepository.add_payload/...):
  tm flow      add-payload     <flow-id> --data-item ID --endpoint 1|2
  tm flow      remove-payload  <flow-id> --data-item ID --endpoint 1|2
  tm flow      list-payloads   <flow-id> [--endpoint 1|2]
  tm data-item list-flows      <item-id>

entity_documents (EntityDocumentRepository — per-kind both sides):
  tm node      link-document   <node-id> <doc-id>     (and unlink-document, list-documents)
  tm container link-document   ...                    (same triplet)
  tm flow      link-document   ...                    (same triplet)
  tm data-item link-document   ...                    (same triplet)
  tm document  list-nodes       <doc-id> [<list flags>]
  tm document  list-containers  <doc-id>
  tm document  list-flows       <doc-id>
  tm document  list-items       <doc-id>
```

All link verbs are idempotent (`INSERT OR IGNORE` at the repo). Re-linking returns `{"linked": false, "reason": "already_linked"}`. Unlink returns `{"unlinked": true|false}`. Reverse listings honor the same `--limit`/`--offset`/`--sort`/`--order`/`--filter` flags as `list`.

### Introspection commands

```
tm schema [<entity>]       -- Pydantic JSON Schema for read + Create + Update models
tm schema --all            -- one document keyed by entity name
tm commands --json         -- machine-readable command tree
```

`tm schema` calls `Model.model_json_schema()`. With no argument, it lists available entity names. With `--all`, it returns `{"document": {...}, "term": {...}, ...}` so an agent can fetch everything in one call.

`tm commands --json` walks `cli.commands` recursively. Stable shape (golden-tested):

```json
{
  "name": "tm",
  "description": "...",
  "subcommands": [
    {
      "name": "document",
      "description": "...",
      "subcommands": [
        {
          "name": "list",
          "description": "...",
          "options": [
            {"name": "--limit", "type": "INT", "required": false, "default": 50, "hidden": false, "description": "..."}
          ],
          "arguments": [...]
        }
      ]
    }
  ]
}
```

Hidden options (the default-diagram-id fallback) emit with `"hidden": true`. `--help` is the human view; `tm commands --json` is the machine view. Agents can fetch the tree once at session start and never re-read help text.

## Existing patterns

The persistence layer is complete and the CLI follows it without divergence. Specifically:

- **Pydantic v2 discriminated unions** on Node and Container (`Annotated[A | B | C, Field(discriminator="type")]`) drive both the repo dispatch and the CLI's per-variant subcommand generation. The CLI iterates `union.__args__` to register subcommands; no introspection trickery beyond `model_fields`.
- **`connect()` context manager** in `src/tm_cli/db/connection.py` — used as-is. Every Click command opens a connection at entry and relies on the manager's commit-on-clean-exit and rollback-on-exception behavior. The error mapper raises `TmError` *inside* the `with connect()` block when needed, which triggers the rollback path before reaching the result callback.
- **`init_schema()`** is process-idempotent (gated by `_initialized_paths` in `connection.py`). Every CLI invocation calls it after `connect()`. No CLI-level caching needed.
- **`load_dotenv()`** at the top of `src/tm_cli/main.py` — kept. The CLI doesn't add other env loading.
- **Repo `search()` uniform contract** (`(text=None, *, **filters, limit=None, offset=0)`) is exposed verbatim per entity as `tm <noun> search <text>`. The CLI's `list` command on entities whose repo `list()` lacks filter parameters (DataItem) routes through `search(text=None, **filters)` to give every entity the same flag set.

There are no existing CLI patterns to follow — the `hello` command in `main.py` is a placeholder. This design establishes the patterns that all future CLI work will inherit.

## Test strategy

`pytest` plus `click.testing.CliRunner` plus Syrupy. Three classes of test, scaling with the cost of getting the contract wrong:

- **`tests/golden/help/`** — one snapshot per command's `--help`. The `--help` text is the agent-facing API contract; drift breaks the contract. Every leaf command in `tm commands --json` must have a corresponding snapshot, enforced by a meta-test that walks the tree.
- **`tests/golden/json/`** — representative invocation per verb per entity (e.g., `node_create_process.json`, `node_list.ndjson`, `node_search_with_type.ndjson`). Volatile fields (timestamps, synthesized ids beyond the deterministic seed) are masked by a custom Syrupy serializer to `"<DATETIME>"` and `"<INT>"`. Errors get one snapshot per exit-code path: not-found (2), validation (1), integrity-UNIQUE/FK/CHECK (3), system-IO (4) — asserting both stderr JSON shape and exit code.
- **Unit tests** — the helpers that don't naturally surface in CLI output: `_errors.map_exception()` (every exception → expected exit code), `_introspection.serialize_command_tree()` (the `tm commands --json` walker), `_options.resolve_default_diagram_id()` (lookup, lookup+create, two-with-name-default, no-default-on-read).

Fixtures:
- `db_with_seed` — `init_schema(":memory:")` plus a deterministic seed (one diagram named "non-default" so default-diagram tests don't collide, one process node, one external-entity, one data-store, one container, one flow, two data-items, two documents, three terms, two observations). Seed is checked in as `tests/fixtures/seed.py` so the test data is itself part of the contract.

Acceptance test:
- `tests/acceptance/test_dfd_workflow.py` — drives the CLI through the agent-cli-design.md golden scenario. Uses only stdout-derived ids. Validates that an agent following the help text alone could complete the workflow.

## Additional considerations

**Constraint name extraction.** `sqlite3.IntegrityError` messages embed the constraint kind in their string (`UNIQUE constraint failed: terms.term`, `FOREIGN KEY constraint failed`, `CHECK constraint failed: ...`). The error mapper parses the prefix to populate the `constraint` field in the error payload. Brittle but standard practice. A test covers each phrase verbatim — if SQLite ever changes wording, the test breaks loudly before the CLI ships drifted output.

**Default-diagram name conflict.** Documented as a v1 quirk above. When the project becomes legitimately multi-diagram, the path is: surface `--diagram-id` (`hidden=False`), add `tm config set-default-diagram <id>` and a per-process default override via `TM_DEFAULT_DIAGRAM_ID`. Out of scope for this design.

**No `tm import`, no schema changes, no workflow state.** Explicit non-goals. Bulk via `--stdin` is the only batch mechanism. Agents handle iteration logic themselves.

**No retry / cache layer.** The CLI is invoked once per agent action; concurrency is single-process and short-lived. SQLite's default locking is sufficient.

**Test-data drift.** Golden snapshots are intentionally fragile. When a snapshot fails, the developer must inspect the diff and either fix the regression or run `pytest --snapshot-update` to bless it. Treat snapshot updates with the same review rigor as schema changes — they're the agent contract.
